# Proma 1:1 复刻

## 用户故事

- 作为熟悉 Proma 的用户，我希望打开 j-gui 后看到接近一致的布局、入口、默认态和操作路径，这样不用重新学习一套桌面 AI 工具。
- 作为从 Proma 迁移过来的人，我希望 Chat、Agent、Settings、工作区、搜索、会话组织和内建快捷键的核心体验都能按同样方式工作，而不是只有名字相似。
- 作为长期使用的人，我希望界面层级、状态反馈、错误提示和空态都尽量和 Proma 对齐，这样不同机器和不同版本之间的心智成本更低。
- 作为维护者，我希望文档里清楚写出哪些是必须追平、哪些是明确排除，这样不会把“暂不纳入”误解成“忘了做”。

## 为什么需要

j-gui 的目标不是“再做一个差不多的 AI 桌面壳”，而是把 Proma 已经验证过的 UI 组织、信息层级和核心交互复用过来。这样可以减少重复设计、降低迁移成本，也能让后续功能扩展建立在一套稳定的产品骨架上。

如果没有一份明确的复刻目标，j-gui 很容易继续朝“能用但粗糙”的方向漂移：入口越来越多、设置越来越散、Chat/Agent/Workspace 各自长成不同风格，最后仍然需要重新统一一次产品语言。把 Proma 当前远程版本当基线，可以把“像不像”变成可检查的问题，而不是主观感觉。

## 怎么解决

先冻结 Proma 当前远程版本作为对照基线，再逐项对齐用户可见的 UI 和行为：布局、导航、设置结构、会话组织、Agent 审批、搜索、输入区、工作区和内建快捷键。

实现层面可以因为 Tauri / j-cli 不同而变化，但外部表现要尽量一致。每个差距都要落到 roadmap 子 feature 或明确排除项里，不能停留在“以后再看”。如果某个能力必须保留，但 j-cli 或现有架构暂时承接不了，也要先写进观察项和路线图，而不是直接缩掉。

## 边界

- 复刻指用户可见的 UI、交互路径、状态反馈、空态、错误态和功能入口一致，不要求源码结构一致。
- 复刻不等于全量复制实现细节；内部模块名、数据结构和技术栈可以不同。
- 明确不需要的功能要单独写进 roadmap / mapping，不要混成“以后再说”。
- 如果某个 Proma 功能与 j-gui 的产品边界冲突，就把它列成排除项，而不是默认删掉。
- 首版明确不纳入：Workspace 管理、BotHub/多人协作、飞书/IM 集成、Tutorial/Onboarding、Proxy 设置、语音输入、应用内更新检查、快捷键自定义、MemOS 记忆、多窗口。
- MCP 只作用于 Agent runtime，不向当前 Chat 路径扩张；如果后续要改这个边界，必须先更新本 req。
