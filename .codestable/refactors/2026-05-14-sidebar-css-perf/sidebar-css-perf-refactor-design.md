# sidebar-css-perf refactor design

## 1. 本次范围

本次 design 不直接实现 scan 中全部候选项，而是先把用户确认过的顶层方向落成统一方案：

- **先做**：侧栏开关性能的架构收敛
- **不按原文推进**：`#2 will-change`、`#4 flexShrink 时机控制`
- **不作为第一步落地**：`#3 右栏关闭时卸载内容` 的零散局部修补
- **已可单独保留**：`#1 minWidth 参与过渡`，但它只解决视觉跳变，不解决“点击后等一会/展开后再卡一下”的主症状

本次 design 关注的不是“某个样式怎么调”，而是以下 3 个结构问题：

1. **开关关键路径过重**
   左右侧栏开关时都夹带了内容挂载、数据读取、滚动恢复、布局测量或重子树重渲染，导致点击和动画首帧被主线程阻塞。

2. **左右侧栏模型不一致**
   左侧更偏向“展开后再挂内容”，右侧更偏向“内容常驻只做宽度隐藏”。两者策略相反，最终都把性能问题带进开关链路。

3. **副作用挂错时机**
   文件树刷新、`scrollIntoView`、Agent split 初始化等副作用直接跟随开关状态，而不是跟随“面板已稳定可见”的时机。

- **预估总工作量**：约 4-6 个文件 / 3 个步骤 / 需要测试 + 人工目视
- **总风险**：中
  原因：会改侧栏内容挂载时机与开关生命周期，但不改用户可见功能、不改 IPC 契约

## 3. 目标架构

### 3.1 统一的侧栏生命周期

左右侧栏统一采用同一种心智模型：

- **Shell（壳层）**：只负责宽度、内边距、透明度、点击命中、展开/收起按钮
- **Content（重内容）**：列表、文件树、拖拽区、附加目录树、滚动恢复、自动定位、副作用

壳层必须满足：

- 点击按钮或快捷键后**立即**响应
- 开关关键路径只允许做：
  - 更新开关状态
  - 更新宽度/内边距 class 或 style
  - 切换 `pointer-events`

重内容必须满足：

- 不在开关首帧里做重挂载/重渲染
- 不在关闭态长期保留无意义订阅
- 只在“面板已稳定可见”后恢复副作用

### 3.2 统一的两阶段策略

建议左右侧栏统一为：

1. **阶段 A：壳层即时开关**
   用户点击、快捷键、程序性开关后，先只切壳层状态，让宽度动画立刻开始。

2. **阶段 B：内容延后接入/延后卸载**
   - 打开时：下一帧或稳定可见后挂入重内容
   - 关闭时：壳层先收起，内容在动画结束后卸载

这个策略比“永远常驻”更容易验证，也比“展开后完整延时再显示全部内容”更能避免明显等待感。

### 3.3 副作用迁移原则

以下逻辑从“开关状态变化”迁移到“内容已挂载且面板稳定可见”：

- 左侧栏：
  - `SessionListItems` 的挂载时机
  - `scrollIntoView`
  - Agent top split 初始化
- 右侧栏：
  - `FileBrowser` / `FileDropZone` / attached dirs 的挂载时机
  - 文件树刷新和自动 reveal
  - 工作区文件路径加载后的首次重内容渲染

原则：**开关先响应，副作用后接入**。

## 4. 执行顺序

### 步骤 1：抽象统一的“侧栏壳层 vs 重内容”边界

- **引用方法**：M-L3-01（职责拆分） + M-L2-01（Extract Function）
- **具体操作**：
  1. 明确 `LeftSidebar` / `SidePanel` 中哪些 JSX 属于 shell，哪些属于 heavy content
  2. 左右两侧都引入同一类挂载状态语义：
     - `isOpen` 或 `sidebarCollapsed` 只控制壳层
     - `contentMounted` 控制重内容是否存在
  3. `AppShell` / `RightPanelSlot` 继续只承载布局和点击命中，不承接重内容时序
- **退出信号**：
  - 代码中能一眼区分壳层和内容层
  - 开关状态不再直接等同于“重内容立即同步进出”
- **验证责任**：AI 自证 + HUMAN 读 diff 判断边界是否清晰
- **回滚**：单步 revert

### 步骤 2：统一开关时序，移除主线程关键路径中的重工作

- **引用方法**：M-L4-03（Lazy Loading） + M-L2-01（Extract Function）
- **具体操作**：
  1. 左侧栏取消“人为整段等待后再展示全部内容”的策略，改为：
     - 壳层立即展开
     - 重内容按统一时序进入
  2. 右侧栏取消“关闭态长期常驻整棵重子树”的策略，改为：
     - 关闭后延后卸载内容
     - 打开时先出壳，再挂内容
  3. 不引入 `will-change`、不引入复杂 JS 动画编排
- **退出信号**：
  - 左右侧栏开关模型一致
  - 快捷键和按钮的开关响应不再被整段内容挂载/常驻拖慢
- **验证责任**：AI 自证 + HUMAN 目视
- **回滚**：单步 revert

### 步骤 3：把副作用迁移到“稳定可见后”执行，并补回归测试

- **引用方法**：M-L2-01（Extract Function） + M-L4-01（渲染路径优化）
- **具体操作**：
  1. 左侧栏的 `scrollIntoView`、Agent split 初始化只在内容已挂载后执行
  2. 右侧栏的文件树相关逻辑只在内容已挂载时参与
  3. 测试覆盖至少包括：
     - 左侧栏展开时重内容不再整段空白等待
     - 右侧栏关闭后重内容最终卸载，重新展开时可恢复
     - `Ctrl+B` 仍可稳定切换左侧栏
     - 会话隔离和 Chat/Agent 模式隔离不回归
- **退出信号**：
  - 相关测试通过
  - 目视确认“点击后立刻开始展开/收起”，且无明显二次卡顿
- **验证责任**：AI 自证 + HUMAN 目视
- **回滚**：单步 revert

## 5. 风险与看点

- **风险 1：打开时内容闪现或空白过久**
  如果挂载时机放得太晚，会把“卡顿”变成“空白等待”。所以打开策略不能再走完整动画后才显示内容。

- **风险 2：关闭时卸载过早导致按钮/布局异常**
  壳层和内容必须彻底拆开，不能让关闭按钮、展开按钮、窗口控制命中依赖重内容容器还活着。

- **风险 3：副作用从开关链路迁走后，选中项定位/文件树恢复时机改变**
  这类行为是允许的实现细节变化，但不能变成“功能丢失”。

- **风险 4：左右侧栏继续各走各的时序**
  这是这次最需要避免的。可以接受参数不同（200ms vs 300ms），但不能接受生命周期模型继续不一致。

## 6. 不做的事

- 不做 `will-change` 这类无 profiling 证据的提示型优化
- 不做 `flexShrink` 的 JS 时机控制
- 不在本轮顺手重构 `FileBrowser`、`SessionListItems` 内部逻辑
- 不改 IPC、Atom 结构或跨前后端契约
- 不把这次工作扩成“全应用性能优化”
